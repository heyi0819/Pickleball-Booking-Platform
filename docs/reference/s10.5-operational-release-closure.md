## Release and deployment procedure

1. Merge only a PR whose head is reviewed, mergeable, clean, and has the five required CI checks successful: Backend build and test, Frontend checks, Clean and forward PostgreSQL migration, Container and optional GCP reference validation, and Zero-cost production-like smoke.
2. Record the immutable main SHA and CI run URL in the release evidence. Do not use a branch-preview URL as final staging evidence.
3. If the release contains a Flyway migration, the Platform Maintainer first takes an encrypted backup and runs the approved image once with the migrator role and `SPRING_PROFILES_ACTIVE=migration`. Verify the highest successful Flyway version and application-role grants. Runtime stays `SPRING_FLYWAY_ENABLED=false`.
4. Deploy the compatible Render release with `WORKERS_ENABLED=false`, exact CORS origins, and secrets sourced only from Render. Verify `/actuator/health` and `/actuator/health/readiness` are `UP` before frontend acceptance.
5. Confirm both Cloudflare Pages production branches are `main`, build the fixed release with Node 24/npm 11, and verify the canonical Pages URLs—not previews—serve the released artifact.
6. Run `bash scripts/current-staging-smoke.sh` from a trusted operator environment. The script is public, read-only, and accepts no secret or token.
7. Run the manual LINE acceptance below. Record only the SHA, time, pass/fail, and non-sensitive error text.

## Post-deploy smoke and LINE checklist

Automated public checks:

- Render `/actuator/health` returns `200` and `UP`.
- Canonical LIFF and Admin roots return `200`.
- Unauthenticated and invalid Platform JWT requests to `/api/v1/me` return `401`.
- LIFF and Admin exact-origin CORS preflights succeed; an unknown origin is `403`.

Manual LINE check:

1. Launch `https://liff.line.me/2011349413-coxfchhN` in a real mobile LINE context.
2. Confirm it returns to `https://pickleball-stg-liff.pages.dev`.
3. Confirm LINE sign-in succeeds, no permanent signing-in state remains, and the STUDENT entry is reachable.
4. If an intentional bootstrap stall occurs, confirm the recoverable error and Retry path are available.

Never attach or record an ID token, Platform JWT, LINE user ID, password, MFA value, Channel Secret, access token, or member screenshot in repository evidence.

## Rollback, forward-fix, and incident response

For a frontend-only regression, roll back the affected Pages deployment only after confirming the compatible API version and canonical production branch. If disabling a frontend, remove its exact CORS origin from Render before or with the disablement.

For a backend regression, use a prior Render release only when it is compatible with the already-migrated schema. Never edit historical Flyway migrations or use a destructive down migration. Schema or data faults require a reviewed forward-fix migration and a new compatible release.

For a suspected credential or LINE compromise: contain the affected consumer, revoke or reissue the credential in its owning provider, update only the authorized consumer, redeploy, then rerun health, CORS, and authentication-boundary checks. For emergency LIFF disablement, remove `VITE_LIFF_ID` from Cloudflare Pages and redeploy, then remove `LINE_LOGIN_CHANNEL_ID` from Render and redeploy. Document incident evidence outside Git without secrets or personal data.

## Database, backup, and isolated restore

Before a migration or destructive recovery action, create an encrypted backup using `scripts/staging-backup.ps1`. It requires an explicit confirmation, `PGSSLMODE=require` for staging, an external backup directory, and an age public recipient. The script dumps only application-owned `public`, encrypts immediately, removes temporary plaintext, writes non-secret metadata, and retains the newest seven archives.

Use `scripts/staging-restore.ps1` only with explicit destructive authorization and only for an isolated target whose database name differs from active `neondb`. Supply the protected age private identity through the maintainer environment; do not upload it. For a clean rehearsal target, install required extensions such as `btree_gist` outside `public`, restore, verify Flyway history and application access boundaries, then remove the rehearsal target when approved.

The staging database remains synthetic-only. Never restore customer or production data into staging, overwrite active staging in a rehearsal, or place archive paths, connection strings, or identity files in Git.

## Monitoring and availability

UptimeRobot is configured only for the public, read-only Render endpoint `https://pickleball-stg-api.onrender.com/actuator/health`, every five minutes. It sends no token, requests no business data, and must not expand to authenticated endpoints. Its purpose is reducing staging cold-start latency for users; it is not a production SLA, an availability guarantee, or authorization to auto-upgrade any plan.

The Staging Infrastructure Owner reviews monitor status and free-tier consumption periodically. If a free quota is at risk, fail closed or pause staging by maintainer decision; do not enable automatic paid overage. A monitor failure starts with public health, last Render deployment, and non-sensitive service logs, followed by the recovery procedure above.
