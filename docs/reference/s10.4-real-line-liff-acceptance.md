# S10.4 Real LINE / LIFF Acceptance

S10.4 enables the existing staging LIFF frontend to use a separately owned, non-production LINE Login channel. The maintainer-approved progressive-profile repair removes phone collection and storage, while preserving the approved LINE credential verification and Platform JWT architecture. It adds no paid resource, production resource, Messaging API channel, webhook, or worker.

## Scope and boundary

| Component | Non-sensitive identifier | Boundary |
| --- | --- | --- |
| LINE provider | `pickleball-stg` | Separate staging-only provider |
| LINE Login channel | `pickleball-stg` (`2011349413`) | Published; no Messaging API resource |

The provider and channel are deliberately separate from the legacy LINE resources. The LIFF app has only the `openid` and `profile` scopes, has `chat_message.write` disabled, and has add-friend disabled.

## Progressive profile and data minimization

The original real-device acceptance exposed an onboarding defect: `profileComplete` treated phone or email as required and the LIFF client redirected a successful LINE login to a mandatory profile form. The repair applies the following product decision:

- Verified LINE subject remains the only trusted external identity; display name and email are not authentication identifiers.
- Initial provisioning uses the verified LINE display name (with the existing safe fallback), locale, active status, and default role assignment.
- `profileComplete` remains in the API for compatibility, but now means platform-required data is present. A provisioned user is complete without email.
- Email remains nullable and can still be updated through `PATCH /api/v1/me/profile`.
- Phone is removed from the user entity, API request/response, OpenAPI source, generated TypeScript client, LIFF UI, tests, and staging schema.

### Forward-only schema change

`V13__remove_user_phone.sql` drops `idx_users_phone` and then `users.phone`. The final `users` shape retains `id`, non-null `display_name`, nullable `email`, status, locale, timestamps, version, and `deleted_at`; its email and status indexes remain. There is no down migration: rollback uses a reviewed forward fix.

The staging boundary is documented as synthetic-only. This environment cannot obtain the maintainer-controlled database query session needed to independently count non-null legacy phone rows, so no staging migration or destructive data action has been run from this session. Before applying V13 to staging, the maintainer must run a value-free count (`SELECT count(*) FROM users WHERE phone IS NOT NULL`) with the staging migrator role. If the count is non-zero and not confirmed synthetic, stop rather than exposing or deleting data.

## Rollback and forward-fix

- To disable this staging login path, first remove `VITE_LIFF_ID` from the Pages build configuration and redeploy, then remove `LINE_LOGIN_CHANNEL_ID` from Render and redeploy.
- To revoke compromised LINE credentials, use the owning LINE Developers Console and update the single staging consumer; do not place replacement values in Git.
- For the privacy repair, apply V13 only after the value-free staging count confirms the approved synthetic-data boundary. If a forward fix is required after migration, add a new migration; never alter V1–V13.
- Do not alter the published staging channel's scopes, add a Messaging API resource, enable a webhook, or alter production resources as part of this slice.
