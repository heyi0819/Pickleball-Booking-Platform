# S11.2A Availability to Student Visibility Trace

## Scope and conclusion

This is a repository trace, not a runtime, provider, or schema change. It records the intended distinction between an approved coach availability and a student-bookable public course.

**Primary classification: A — EXPECTED DOMAIN BEHAVIOR.** An approved `AvailabilityProposal` is a coach-supply input. It is visible to an authenticated student in the lesson-demand flow so that the student can create a selected-availability `LessonRequest`; it is not, by itself, an `OPEN` `CourseOffering`, a `CourseSession`, or a direct enrollment target.

Consequently, an approved availability must not be expected in the LIFF **公開課程 / 開放報名** list. That list intentionally contains only published `OPEN` offerings. If an approved availability is absent from the LIFF **找教練時段** selector for a student in the same organization and future time range, collect the authenticated request/response evidence before classifying a separate scope or data defect.

## Availability approval trace

1. `CoachController.reviewAvailability` handles `POST /api/v1/coach-availability-proposals/{id}/review`.
2. `CoachService.reviewAvailability` is transactional. It loads the proposal, requires organization-scoped `COMMITTEE` authorization (or global `PLATFORM_ADMIN` through the shared access policy), and calls `AvailabilityProposalEntity.review`.
3. The entity permits only `SUBMITTED -> APPROVED` or `SUBMITTED -> REJECTED`; approval writes `status`, `reviewed_by`, `reviewed_at`, and `review_note` to `coach_availability_proposals`.
4. The same transaction records `AVAILABILITY_APPROVED` through `AuditOutboxService`. It does not create an offering, offering session, course, enrollment, schedule reservation, or student-publication projection.

Approval is therefore only availability approval and does not create a student-bookable resource.

## Database relationship map

```text
coach_availability_proposals (APPROVED)
  └─ selected by lesson_requests.selected_availability_proposal_id
       └─ on LessonRequest submission: coach_availability_claims (ACTIVE)
            └─ CourseMatch / confirmed Course path when operationally completed

course_offerings (DRAFT -> OPEN -> CLOSED -> CONFIRMED)
  ├─ course_offering_sessions
  ├─ course_offering_price_snapshots (CONFIRMED before publication)
  ├─ course_offering_registrations
  └─ schedule_reservations (per offering session and participant)
       └─ on confirmation: courses / course_sessions / enrollments
```

`V3__coach_supply_lesson_demand.sql` defines availability proposals, lesson requests, and claims. `V8__open_enrollment_persistence.sql` separately defines offerings, offering sessions, price snapshots, registrations, and the dual-source reservation model. There is no foreign key, trigger, or application command that turns an availability approval into an offering row.

## Student API and LIFF trace

| Student intent | API/read model | LIFF component | Visibility rule |
|---|---|---|---|
| Select a coach time for a demand | `GET /api/v1/coach-availability-proposals/available` → `CoachService.approvedAvailability` → `coach_availability_proposals` | `StudentLessonDemand` | Active `STUDENT`, exactly one server-resolved organization, `APPROVED`, and `start_at > now()` |
| Create a demand from that time | `POST /api/v1/lesson-requests`, then submission and claim | `StudentLessonDemand` | Selected availability must be approved, same organization, future, and belong to an approved coach |
| Browse directly bookable group classes | `GET /api/v1/course-offerings?status=OPEN` → `CourseOfferingQueryService.list` → offering/session/price/registration read query | `StudentOpenEnrollment` | Active `STUDENT` role in the offering organization and `o.status='OPEN'` |
| See formed teaching sessions | `GET /api/v1/courses` and course-session reads | `StudentCourseOperations` | Enrollment and organization-scoped course access |

`StudentOpenEnrollment` deliberately sends `status: "OPEN"`; it does not call the availability endpoint. `StudentLessonDemand` deliberately calls the availability endpoint and constructs a Lesson Request with the selected proposal, coach, time, and optional preferred venue. The two views serve different product flows.

## Intended operational flows

### Demand and supply matching

```text
Coach availability approval
→ student selects it in 找教練時段
→ student submits Lesson Request / active Availability Claim
→ admin or committee creates and completes Course Match
→ coach accepts invitation, venue/pricing/readiness are confirmed
→ confirmed Course and CourseSession
→ enrolled student sees course/session
```

### Open enrollment

```text
Admin or committee creates DRAFT CourseOffering
→ supplies approved coach, session plan, venue snapshot, capacity, and price snapshot
→ publishes OPEN offering
→ student sees 公開課程 / 開放報名 and may register
→ CLOSED and confirmed offering creates the formal Course downstream
```

An approved availability may inform either operation, but it is not a substitute for the required offering/session, publication, capacity, pricing, or organization state.

## Admin-first pilot and authorization alignment

The backend uses the same domain capability with role-aware authorization and server-owned organization scope; it does not duplicate APIs by UI role.

| Capability | PLATFORM_ADMIN | COMMITTEE | COACH | STUDENT |
|---|---|---|---|---|
| Review coach application and availability | Global access through the shared organization access policy | Allowed within assigned organization | No | No |
| Create, price, publish, close, or confirm offering | Global access through the shared policy | Allowed within assigned organization | No | No |
| Create and submit own availability | Not an ownership role | No | Own approved profile only | No |
| Select approved availability / create demand | May operate only through its applicable workflow context; not a student-facing publication right | No | No | Own organization, future approved availability only |
| Browse OPEN offerings / register | Global operational read where authorized | Organization operations view | Own-coach visibility where authorized | OPEN offerings in assigned organization |

For the pilot, `PLATFORM_ADMIN` can use the existing management APIs and Admin web application as the operational control path. The API authorization already recognizes global platform administration. The LIFF role picker intentionally exposes only `STUDENT`, `COACH`, and `COMMITTEE`; that is a UI-role choice, not a backend authorization failure. Committee UI parity outside existing management views is future S11.3 role-delegation/UI enablement work, not an S11.2A blocker.

## S11.2A acceptance

The valid end-to-end criterion is:

> Approved availability is available to the management and student-demand workflow, and the resulting published offering or confirmed course/session becomes student-visible through its own read model.

No repair, migration, API change, authorization expansion, or paid resource is required by this trace. A separate defect exists only if a future approved proposal in the same resolved student organization is missing from `GET /coach-availability-proposals/available`, or if an `OPEN` offering is missing from `GET /course-offerings` for that student; either case requires request/response evidence before a repair.
