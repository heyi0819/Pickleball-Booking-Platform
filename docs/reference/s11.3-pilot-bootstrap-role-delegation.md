# S11.3 Pilot Bootstrap and Role Delegation

## Controlled first PLATFORM_ADMIN bootstrap

There is no public self-service role grant. A user must first complete normal LINE login so an active `users` record exists. A maintainer then runs the backend as a local, non-web command with the `pilot-bootstrap` profile and both explicit values below supplied outside the repository:

```text
--spring.profiles.active=pilot-bootstrap
--spring.main.web-application-type=none
--pilot.bootstrap.confirm=grant-initial-platform-admin
--pilot.bootstrap.platform-admin-user-id=<existing-user-uuid>
```

The command rejects a missing confirmation, inactive or unknown user, and any attempt once an active global PLATFORM_ADMIN already exists. It records `PLATFORM_ADMIN_BOOTSTRAPPED` in `audit_logs`. It does not create a secret, identity, organization, provider resource, or network endpoint.

## Committee delegation

Only a global PLATFORM_ADMIN may search active users and grant or revoke COMMITTEE for an explicit active organization. COMMITTEE assignments are organization-scoped; PLATFORM_ADMIN remains global (`organization_id = NULL`). The existing partial unique indexes prevent duplicate assignments. Grant, reactivation, and revoke are audited as `COMMITTEE_ROLE_GRANTED` and `COMMITTEE_ROLE_REVOKED`.

## Conflict and scope rules

- A reviewer cannot approve or reject their own coach application or availability proposal.
- A refund requester cannot review their own refund.
- COMMITTEE capability checks derive scope from active server-side assignments. A global PLATFORM_ADMIN may select an explicit organization; the client selection does not grant a role.
- The Admin Portal is shared. COMMITTEE sees its own organization operations; PLATFORM_ADMIN has a global organization selector and role-delegation panel.
