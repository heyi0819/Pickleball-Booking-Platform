# S10.2 Secrets / Database Roles / Backup-Restore Baseline

S10.2 contains repository-side operational controls only. It does not create Neon, Render, Cloudflare, or LINE resources, deploy an application, or add product behavior.

## Secret inventory

| Item | Class | Owner and storage | Consumer | Rotation / revocation |
| --- | --- | --- | --- | --- |
| `VITE_API_BASE_URL`, `VITE_LIFF_ID` | Public build-time | Cloudflare Pages environment | frontend build | replace next build; no secret revocation required |
| `JWT_SIGNING_SECRET` | Server secret | maintainer-owned Render secret store | backend runtime | deploy with new secret, retain old only for approved overlap, then revoke |
| app and migrator passwords | Server secrets | maintainer-owned Render/secure local store | runtime / manual migration only | set a new password, update one consumer, verify, revoke old password |
| LINE token/channel secret | Server secret | maintainer-owned secret store | backend later | revoke/reissue in LINE console, then update runtime |
| `APP_CORS_ALLOWED_ORIGINS`, `WORKERS_ENABLED`, `PORT` | Server non-secret config | Render environment | backend runtime | update configuration and redeploy only when approved |
| age public recipient | Public encryption config | this runbook / maintainer procedure | backup script | replace recipient after identity rotation |
| age private identity | Secret | maintainer offline protected storage | local restore only | create replacement identity, re-encrypt retained backups, revoke old storage access |

Never place server secrets in Vite variables, Git, CI logs, PR text, or backup filenames.

## PostgreSQL role model

The provider/database owner remains maintainer-only. `pickleball_migrator` is a login role used only for controlled Flyway runs. It has `CONNECT`, `USAGE`, and `CREATE` on `public`; it owns migration-created objects. `pickleball_app` is a separate runtime login role with `CONNECT`, schema `USAGE`, and DML/sequence privileges granted by the migrator's default privileges plus explicit grants for existing objects. It has no schema ownership or general DDL privilege.

After each migration, the migrator grants existing table and sequence privileges to the app role and verifies `flyway_schema_history`. Runtime uses `DATABASE_USERNAME=pickleball_app` and `SPRING_FLYWAY_ENABLED=false`.

## Controlled migration

1. Record release SHA and create an encrypted pre-migration backup when state exists.
2. Connect with the migrator credential using a PostgreSQL JDBC URL with `sslmode=require`.
3. Run the fixed release image with `SPRING_PROFILES_ACTIVE=migration`.
4. Verify the highest successful Flyway version and app-role grants.
5. Remove migrator values from the runtime path; start with `pickleball_app`, Flyway disabled, workers disabled.
6. Check readiness and representative unauthenticated `401` behavior; store evidence outside Git.

Failures use forward-fix only. Historical migrations are never edited.

## Encrypted backup and isolated restore

`scripts/staging-backup.ps1` creates a custom-format `pg_dump` of the application-owned `public` schema (including Flyway history), encrypts it immediately with age X25519 recipient `age1yp7p697sexzjzupzkrsvjng5th3kg9e60e732whl3kza8svw4g4sv3d7vz`, removes the temporary plaintext, writes non-secret metadata, and retains the newest seven archives. Provider-managed schemas, including Neon `neon_auth`, are intentionally excluded. Backups must be written outside the repository.

`scripts/staging-restore.ps1` requires the maintainer-local private identity, an explicit isolated target database, and a destructive confirmation token. It refuses a target whose `PGDATABASE` equals the supplied active database identifier. It decrypts only to a temporary file and removes it after `pg_restore`. For a clean PostgreSQL rehearsal target, install required provider-independent extensions such as `btree_gist` in a non-`public` schema before the restore, so the archive can safely recreate `public`.

Metadata records UTC timestamp, environment, Git SHA, Flyway version, database identifier, and ciphertext SHA-256. The backup uses standard PostgreSQL tools and remains portable to future NAS hosting.

## Synthetic data and recovery policy

Staging contains only synthetic organizations, members, coaches, students, and financial data. The maintainer owns seeds/reset actions. A reset needs explicit destructive authorization, an encrypted backup first, and evidence of cleanup. Never import customer or production data.

For suspected leakage: disable the affected credential, revoke/reissue it at its owner, update the single authorized consumer, verify readiness and access boundaries, then document the incident outside Git. The public age recipient is replaceable; the private identity is never uploaded or logged.
