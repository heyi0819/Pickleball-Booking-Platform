# S11.4 Backup / Restore / Operational Readiness

## Scope and recovery class

S11.4 defines the zero-cost pilot's controlled PostgreSQL logical backup and isolated restore procedure. It does not activate GCP, modify Neon/Render/Cloudflare/LINE resources, add a paid service, upload an archive to GitHub, or start S11.5.

The pilot recovery targets are **RPO <= 24 hours** and **RTO target <= 8 hours, best effort**. They are pilot targets, not an SLA or HA guarantee.

The target flow is:

```text
Neon PostgreSQL (TLS) -> pg_dump custom format -> age encryption -> controlled local storage / existing controlled Drive
                                                -> isolated local PostgreSQL 18 restore rehearsal
```

Only the application-owned `public` schema is exported. Neon-managed schemas are intentionally excluded. The archive name is `pickleball-<environment>-<UTC timestamp>.dump.age`; it has no password, connection string, database identifier, or personal data in its filename. A same-named non-secret JSON sidecar records UTC time, Git SHA, Flyway version, and ciphertext SHA-256.

## Controlled backup procedure

`scripts/staging-backup.ps1` is the Windows-first procedure. It requires PostgreSQL 18 client tools, `age`, a public age recipient, and `PGHOST`, `PGDATABASE`, `PGUSER`, and `PGPASSWORD` supplied only through the maintainer's secure local process environment. For staging, `PGSSLMODE=require` is mandatory.

The command validates all local prerequisites before it makes a database connection. `-DryRun` validates the command, confirmation, tooling, archive location, and recipient format without connecting, dumping, encrypting, or deleting anything.

The maintainer must choose an external controlled folder, never a repository folder. On successful dump, the script encrypts to a unique temporary ciphertext file, verifies it is non-empty, atomically moves it to the final `.dump.age` name, then writes its checksum metadata. The temporary plaintext dump is removed in `finally`, including on failure. A partial ciphertext is also removed on failure. The script does not print environment values, file contents, or secret material.

The identity path is provided to the restore process only through `AGE_IDENTITY_FILE`; for the current staging custodian it points to `C:\Users\s0910\.pickleball\staging-backup-age-key.txt`. The identity itself must never be opened, printed, copied into Git, or passed in a command-line value.

After encryption, manually copy only the `.dump.age` plus its non-secret metadata file to an existing controlled Google Drive folder if one is already available. Do not create Drive credentials or another storage provider for this procedure.

## Retention

The default retention is **35 days**. After a successful new archive, the script deletes only files below the explicitly selected backup directory that exactly match the current environment's archive naming pattern and whose filesystem UTC timestamp is older than 35 days. It removes the matching sidecar only when the matching archive is selected. It never recursively deletes a directory or touches plaintext dump files outside its own temporary file.

Use `-RetentionDays 35` explicitly in operator evidence. A custodian may perform the same matching-name/date review manually before running the procedure when a retention deletion needs extra scrutiny.

## Isolated PostgreSQL 18 restore rehearsal

`scripts/staging-restore.ps1` accepts only a local target host (`localhost`, `127.0.0.1`, or `::1`) and a database name beginning with `pickleball_restore_`. It also rejects the supplied active database name. These are independent guards against restoring into the active Neon pilot database.

Prepare a disposable PostgreSQL 18 local/container target before the restore. Preinstall `btree_gist` outside `public` (for example in an `extensions` schema) so the archive can recreate `public`. Set local target connection variables through the trusted process environment; do not reuse the Neon connection settings for the target.

The restore validates, without selecting PII:

- the decrypted file is a readable PostgreSQL custom archive;
- `flyway_schema_history` reaches the repository's latest version;
- `btree_gist` is available;
- required tables exist: users, organizations, user roles, coach availability, lesson requests, offerings/sessions/registrations, receivables/payments/refunds, audit logs, and outbox events;
- representative UUID, `TIMESTAMPTZ`, and `NUMERIC` column shapes exist;
- non-sensitive row-count queries for users, organizations, audit logs, and outbox events execute.

Temporary decrypted dumps are created only in the OS temporary directory and removed in `finally`. Destroy the isolated target after the maintainer has recorded a pass/fail summary and no longer needs it.

## Failure and incident handling

| Failure | Detection / immediate action | Recovery / escalation |
| --- | --- | --- |
| `pg_dump` or network failure | Non-zero script result; no final archive is published | Keep existing archive, verify Neon availability/TLS/credential expiry, retry only after correction; escalate if RPO is at risk. |
| age encryption failure or insufficient disk | Non-zero result; partial ciphertext and plaintext temp file are cleaned | Free controlled local space or repair age tooling; do not retain plaintext manually. |
| corrupted archive / wrong key | Decryption or `pg_restore --list` fails | Verify ciphertext SHA-256 and select the prior encrypted archive; if none restore, classify P0. |
| restore validation failure | Script rejects Flyway/table/type/extension mismatch | Preserve the failed isolated target for evidence only if safe; use a compatible PostgreSQL 18 target and forward-fix schema issues. Never overwrite active Neon. |
| Neon unavailable, Render unavailable while DB healthy | API health/readiness or provider status fails | Use existing archive/restore procedure for data recovery only; handle Render deployment separately through S10.5 release recovery. |
| accidental schema/data damage | Audit/monitor/operator report | Classify P0, stop destructive actions, identify last known-good archive, obtain explicit restore authorization, rehearse isolated restore first, then make a separately authorized recovery decision. |
| expired or rotated password | Auth failure without logging credentials | Rotate at the owning provider, update the one authorized consumer, re-run backup/health checks. |

## Pilot incident and ownership model

The pilot uses a single maintainer / solo custodian. This is not dual-control. Compensating controls are MFA, least privilege, separate app/migrator roles, audit records, no long-lived credentials in Git, and explicit authorization for destructive or provider actions.

| Responsibility | Pilot owner |
| --- | --- |
| backup, 35-day cleanup, and restore rehearsal | Platform Maintainer / Backup Custodian |
| emergency restore decision and credential rotation | Platform Maintainer with explicit maintainer authorization |
| provider dashboard and free-tier quota checks | Staging Infrastructure Owner |
| incident classification and external communication | Platform Maintainer |

Pilot severity is deliberately small: **P0** data loss/corruption, unauthorized privileged access, or impossible restore; **P1** login/API/database outage or blocked payment/refund workflow; **P2** degraded UI, monitoring gap, expected cold start, or non-critical Admin issue. P0 requires immediate containment and an explicit recovery decision; P1 requires same-day owner action; P2 is tracked for the next maintenance window.

## Monitoring boundary

UptimeRobot Free monitors only Render's public read-only `/actuator/health` endpoint. The operational runbook also requires checking the canonical LIFF and Admin URLs during release/incident handling. Missing dedicated frontend monitors remain a **P1 improvement**, not an S11.4 P0 blocker. No paid monitoring or automatic provider upgrade is authorized.
