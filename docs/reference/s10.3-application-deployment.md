# S10.3 Application Deployment

S10.3 establishes the first persistent, non-production staging deployment. It adds no product capability, Flyway migration, paid provider resource, real LINE resource, or production resource.

## Staging boundary

| Component | Non-sensitive identifier | Boundary |
| --- | --- | --- |
| Neon PostgreSQL | project `pickleball-stg`, database `neondb`, Singapore | Free, synthetic-only staging database |
| Render API | `pickleball-stg-api` | Free Java 21 Docker web service |
| Cloudflare Admin | `pickleball-stg-admin.pages.dev` | Free Pages project from `main` |
| Cloudflare LIFF | `pickleball-stg-liff.pages.dev` | Free Pages project from `main`; no real LINE LIFF configured |

The deployed release is main commit `fa4215ef2bdf5b531fe9f26956cdf4161a892335`. Provider passwords, connection strings, JWT material, age identities, and provider tokens are never recorded in Git.

## Database and migration evidence

The maintainer-controlled Neon owner created separate login roles:

- `pickleball_migrator` is used only for controlled Flyway runs.
- `pickleball_app` is the Render runtime role, with DML and sequence access but no general DDL authority.

The maintainer ran the current release's forward-only Flyway migration through `pickleball_migrator`. Versions `V1` through `V12` are successful. Temporary database `CREATE` permission needed for the existing `btree_gist` baseline extension was revoked after the migration. Render runs with `SPRING_FLYWAY_ENABLED=false` and `WORKERS_ENABLED=false`.

## Provider configuration

### Render

The runtime listens through Render's injected `PORT` and receives the following non-secret configuration:

```text
SPRING_FLYWAY_ENABLED=false
WORKERS_ENABLED=false
APP_CORS_ALLOWED_ORIGINS=https://pickleball-stg-admin.pages.dev,https://pickleball-stg-liff.pages.dev
```

Database credentials and `JWT_SIGNING_SECRET` are maintained only in Render's secret store. The database connection uses TLS (`sslmode=require`).

### Cloudflare Pages

Both Pages projects build from the `frontend` root using the committed Node 24 configuration and npm 11:

| Project | Build command | Output | Public build variable |
| --- | --- | --- | --- |
| `pickleball-stg-admin` | `npm ci && npm run build --workspace @pickleball/admin` | `apps/admin/dist` | `VITE_API_BASE_URL=https://pickleball-stg-api.onrender.com/api/v1` |
| `pickleball-stg-liff` | `npm ci && npm run build --workspace @pickleball/liff` | `apps/liff/dist` | `VITE_API_BASE_URL=https://pickleball-stg-api.onrender.com/api/v1` |

`VITE_LIFF_ID` intentionally remains unset. The LIFF frontend is therefore a public HTTPS build only; it must not be treated as an enabled real LINE entry point until a separately approved LINE staging setup exists.

## Backup and isolated restore evidence

The maintainer ran `scripts/staging-backup.ps1` against staging with credentials supplied through a local secure prompt. It produced an age-encrypted custom-format archive and non-secret metadata outside this repository; the temporary plaintext dump was removed. The archive contains the application-owned `public` schema and intentionally excludes Neon-managed schemas.

The maintainer then restored that archive using `scripts/staging-restore.ps1` into a new local PostgreSQL 18 Docker database named `pickleball_restore_rehearsal`. The target was checked to be distinct from active staging `neondb`, used only for the rehearsal, and was removed afterwards. `btree_gist` was preinstalled in a separate `extensions` schema so the clean restore could recreate `public`. The restored database reported 12 successful Flyway migrations, matching staging `V1` through `V12`.

The maintainer-owned age private identity remained outside Git and CI throughout the rehearsal.

No plaintext dump, backup archive, metadata artifact, secret, or connection string may be committed.

## Forward fix and rollback

- For frontend regression, roll back the affected Pages deployment or remove the affected origin from the Render allowlist before disabling the corresponding Pages project.
- For backend regression, use Render's prior release only after confirming that its database compatibility is safe; migrations remain forward-only and require a forward fix.
- For credential suspicion, rotate and revoke only in the owning provider, update the single consuming service, then re-run health and access-boundary checks.
- Never overwrite active staging during a restore rehearsal.
