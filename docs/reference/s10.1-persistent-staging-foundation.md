# S10.1 Persistent Staging Foundation

S10.1 prepares repository configuration for persistent staging. It does not deploy, create provider resources, create secrets, or connect a real LINE channel.

## Boundary and names

The staging identifier is `pickleball-stg`. The intended provider boundary is Cloudflare Pages for static LIFF/Admin builds, Render Free for the Java 21 Docker API, Neon Free PostgreSQL in Singapore, and separate LINE staging channels. These resources and their future production equivalents remain separate.

Provider HTTPS URLs are inputs, not source code constants. Custom domains, GCP paid deployment, keep-alive workers, and any paid overage are out of scope.

## Environment contract

| Variable | Owner | Secret | Purpose |
| --- | --- | --- | --- |
| `VITE_API_BASE_URL` | Cloudflare Pages build | No | Render API URL ending in `/api/v1` |
| `VITE_LIFF_ID` | Cloudflare Pages build | No | Dedicated staging LIFF ID |
| `APP_CORS_ALLOWED_ORIGINS` | Render runtime | No | Comma-separated exact Pages origins; empty denies every cross-origin request |
| `PORT` | Render runtime | No | HTTP listen port; defaults to `8080` locally |
| `DATABASE_URL` | Render runtime secret | Yes | Neon PostgreSQL JDBC URL with `sslmode=require` |
| `DATABASE_USERNAME`, `DATABASE_PASSWORD` | Render runtime secrets | Yes | Application role credentials |
| `JWT_SIGNING_SECRET` | Render runtime secret | Yes | Platform JWT signing secret |
| `LINE_LOGIN_CHANNEL_ID`, `LINE_MESSAGING_CHANNEL_ACCESS_TOKEN` | Render runtime secrets | Yes | Dedicated staging LINE configuration |
| `WORKERS_ENABLED` | Render runtime | No | Defaults to `false`; any worker run is acceptance-only |

Never use a `VITE_*` variable for secrets. No actual values belong in Git.

## Cloudflare Pages build setup

The frontend workspace pins Node through `frontend/.nvmrc` (`24`) and npm through `frontend/package.json` (`npm@11.17.0`). In each Pages project set `NODE_VERSION=24`; use the `frontend` directory as the root directory and run `npm ci && npm run build`.

| Pages project | Build output directory | Required public build values |
| --- | --- | --- |
| `pickleball-stg-liff` | `apps/liff/dist` | `VITE_API_BASE_URL`, `VITE_LIFF_ID` |
| `pickleball-stg-admin` | `apps/admin/dist` | `VITE_API_BASE_URL`, `VITE_LIFF_ID` only if its UI later consumes LIFF configuration |

Pages must receive the same fixed API base URL for a release. The API value uses the provider HTTPS domain directly; Firebase rewrites are not part of this staging path.

## Render Docker foundation

Render builds from repository root with Docker context `backend` and Dockerfile `backend/Dockerfile`. The image already exposes port `8080`; `server.port=${PORT:8080}` accepts Render's injected port and Spring listens on its standard container interface. Readiness is `/actuator/health/readiness` and the public API base is `/api/v1`.

Start the web service with `WORKERS_ENABLED=false` and `SPRING_FLYWAY_ENABLED=false`. Before a new runtime version, the maintainer performs one controlled, forward-only Flyway run using the same image and the migration profile. A failed migration is handled by forward-fix; do not start the API against an unverified schema.

## Neon PostgreSQL foundation

Use a standard PostgreSQL JDBC URL, for example `jdbc:postgresql://<neon-host>/<database>?sslmode=require`. Create a least-privilege application role for the runtime and reserve a separate future migrator role for the maintainer-controlled Flyway run. The repository has no Neon-specific data access behavior; Flyway remains forward-only and is disabled in the normal runtime after the controlled migration.

Keep the latest seven encrypted logical backups outside the runtime filesystem. Restore drills and backup automation are follow-up operational work, not part of S10.1.

## CORS security contract

Only exact origins in `APP_CORS_ALLOWED_ORIGINS` may call `/api/**` from a browser. The default is an empty allowlist. The backend accepts necessary API methods and `Authorization`, `Content-Type`, `Idempotency-Key`, and `X-Request-Id` headers, does not use wildcard origins, and does not enable credentialed CORS. Platform JWT authentication and every existing authorization rule remain unchanged.

Before S10.2, record the two actual Cloudflare HTTPS origins in Render and validate: approved-origin preflight succeeds, unknown-origin preflight fails, and an unauthenticated request from an approved origin still returns `401`.

## Rollback

No provider state exists after this PR. Revert the PR to remove the repository foundation. After a later deployment, first remove the affected Pages origin from `APP_CORS_ALLOWED_ORIGINS` or roll back the Render image, then use a forward-fix for any database issue; never rely on destructive down migrations.
